# Robot Daemon 更新系统设计

> 对应英文原文：[`updater-design.md`](updater-design.md)

## 1～3. 目标和原则

设备应在没有 SSH 人工介入时安全更新，并在坏版本下恢复。更新覆盖守护进程和独立模型组件，不负责整个 Linux 或全部外设固件。

原则包括：设备有网络；manifest 描述并签名；release 不可变；切换原子化；应用后经过健康门；`btd`/`updaterd` 在 `robotd` 损坏时仍工作；设备状态独立保存。

## 4. 架构

`updaterd` 拥有状态机，下载后验证签名和摘要，安装到版本目录并切换 `current`。手机、BLE 和 `robotctl` 只是触发器。

## 5. 更新模型

通道表达稳定性；manifest 记录版本、文件、摘要、组件、最低版本和钩子；板载公钥验证签名。签名不自动防止降级，因此还需要最低版本和策略。

每个运动模型计划独立版本化。设备身份、校准、网络和用户设置放在 release 外。

## 6. 托管

长期设备不应依赖私有仓库 token。正式制品适合公开读取并由签名建立信任。

## 7. 状态机

检查 → 下载 → 验证 → staging → 预检 → 安装 → 切换 → 重启 → 健康检查 → 提交或回滚。预检包括空间、兼容性、当前事务和 unit 风险。

## 8. 健康门和回滚

新版本达标后才成为 active；失败切回 golden。更新器保存持久摘要和运行 transcript。最低版本/kill switch 可拒绝危险旧版。

## 9. 安装钩子

全新安装需要的系统配置，在旧设备首次升级到该功能时也必须由幂等 postinstall 补齐。钩子使用受控环境并记录输出。

## 10～13. 配置、范围和手机

`updater.toml` 描述多个组件和健康规则。OS、bootloader、MCU 等暂不属于当前 OTA。手机经 BLE 可检查、应用、看进度和请求回滚；长任务不能堵塞 BLE。

## 14～17. 测试、发布和未来

无硬件测试覆盖签名、下载、安装、systemd 和回滚；真机测试覆盖 eMMC、重启、控制循环和媒体。候选通道先小范围验证，再推广。未来包括模型 Hub、多硬件和自主行为配置。
