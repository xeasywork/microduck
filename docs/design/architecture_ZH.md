# Robot Daemon 总体架构

> 对应英文原文：[`architecture.md`](architecture.md)

## 系统形态

系统拆成多个故障域：`robotd` 管运动，`mediad` 管摄像头和 WebRTC，`tofd` 管深度，`padd` 管手柄，`btd` 管 BLE，`configd` 管配置，`updaterd` 管更新。

## 1. 服务与不变量

- 只有 `robotd` 拥有 Dynamixel 总线。
- 运动安全不依赖摄像头、蓝牙或网络。
- `updaterd` 和配置路径在 `robotd` 损坏时仍能工作。
- 媒体故障不能拖垮控制循环。
- 控制循环不能等待 socket、网络、磁盘或相机。

## 2. 进程间通信

控制面使用 JSON-RPC 2.0，适合低频可靠命令；数据面承载视频、音频、深度和高速输入。等待 I/O 的外围使用异步，50 Hz 控制保持同步和固定预算。

感知应靠近传感器：摄像头输出目标和方位，ToF 输出距离和障碍特征，`robotd` 不读取原始像素。

## 3. 状态所有权

每份状态只有一个所有者。Wi-Fi 属于 `configd`，电机和策略属 `robotd`，安装选择属 `updaterd`；其他服务通过 API 请求修改。

## 4. 统一机器人 API

同一 API 可经 BLE、Unix socket、WebRTC 和未来 WebSocket 传输。BLE 只开放配网、状态和更新等子集；传输层不复制业务逻辑。客户端只能发送意图，不能直接写电机。

## 5. 远程访问

WebRTC 承载媒体和可靠控制；未来 teleop 使用不可靠、带序号的通道。服务端 LLM 更适合 WebSocket、按需 JPEG 和状态对象，而不是解码 30 fps 视频。该 WebSocket 尚未实现。

公网访问还需要信令、STUN、TURN 和认证基础设施。

## 6. 安全与控制权

安全层最终裁决所有动作。多控制来源必须有明确优先级；断线后回到停止或稳定姿态；大模型和远程客户端不能绕过跌倒、温度和关节限制。

## 7. 隐私

摄像头和麦克风位于家庭环境中。远程会话、持续感知和社交模式需要显式同意、可见状态和关闭能力。

## 8～10. 可观测性、问题和顺序

每个服务记录进程 revision、可执行路径和健康信息。先建设安全本地控制和统一 API，再完成更新、媒体、远程入口，最后建设自主行为和 Agent。
